# 01 理解產品：先當使用者

影片能賣的，只有「產品真的做得到」而且「鏡頭拍得出來」的東西。這一步的目的是建立這兩份清單。

## 1. 讀文件，回答四個問題

讀 README、PRODUCT/DESIGN 文件、首頁文字、程式裡的設定檔：

1. **誰在用？解決什麼痛？**（沒寫就問使用者，不要自己編）
2. **核心機制是什麼？**（資料從哪來、怎麼計算、輸出什麼）
3. **資料是真的還是模擬的？** 有沒有示範參數？→ 影片要怎麼標示
4. **視覺系統**：色票、字型、語意色（哪個顏色代表正常、警告、能源……）→ 之後影片沿用

## 2. 把產品跑起來，逐一操作

```bash
npm install && npm run build && cd dist && python -m http.server 8766   # 或專案自己的啟動方式
```
用 Playwright 開啟，先列出所有可操作元素：
```python
btns = await pg.eval_on_selector_all("button,[role=button],a", "els=>els.map(e=>(e.innerText||e.getAttribute('aria-label')||'').trim()).filter(Boolean)")
```
然後**每個功能都操作一次、截一張圖**（操作前後各一張更好），拼成總覽圖親眼看。

## 3. 建立功能清單

| 功能 | 操作方式 | 畫面上的變化 | 影片裡看得清楚嗎？ | 對觀眾的價值 |
|---|---|---|---|---|
| 例：情境切換 | 點「雲層遮蔽」 | 太陽能 27→8 kW、購電上升、趨勢圖轉折 | 數字小 → 需推鏡 | 決策前先模擬（高） |

「看得清楚嗎？」的判斷方法：把截圖縮到 960×540（一般人在手機或投影上看影片的有效解析度），還看得出變化嗎？

## 4. 找 money shot

產品最「哇」的那一刻，通常是以下之一：
- 一個動作引發大量連動（點一下，3D、數字、圖表同時變）
- 看見原本看不見的東西（能量流、資料流、隱藏的關係）
- 從宏觀到微觀的連續性（整座工廠 → 一台機器 → 一個數字）
- 前後對比非常明顯的情境

money shot 要放在故事的高點，並且用最好的鏡頭拍（電影鏡頭、推鏡、留足時間）。

## 5. 可視性問題與改程式建議

常見問題與建議改法：

| 問題 | 例子 | 建議 |
|---|---|---|
| 狀態變化太細微 | 圖層只改一點點顏色 | 加強顏色對比、加粗加亮粒子／線條 |
| 鏡頭預設差異太小 | 「內部視角」只是拉近一點 | 改成真的進到場景內、或在影片用拖曳運鏡 |
| 介面元素太小 | 9px 標籤 | 不必改，影片推鏡即可 |
| 每次開啟狀態不同 | localStorage 記住上次設定 | 錄影時清除；或加 `?demo` 參數固定初始狀態 |
| 有提示文字、游標說明 | 「拖曳旋轉」 | 錄影時用 CSS 隱藏 |

回報給使用者時分三類：**建議改**（後製補不了）、**可改可不改**（後製補得了）、**不用改**。附理由與預估改動量。使用者改完、重新 build 之後再進入拍攝。

- 功能清單（含可視性判斷與價值）

- 色票、字型、語意色
- 誠實標示需求（模擬資料、示範參數、未完成功能）
